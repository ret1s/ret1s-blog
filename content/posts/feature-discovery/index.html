Feature Discovery, not Model Engineering

Author: geohanz · Date: 2026-06-19

§1The diagnosis

Active equity is governed by the full Fundamental Law of Active Management:

IR ≈ IC · √BR · TC
IC = Information Coefficient (forecasting skill — correlation between signal and forward return)
BR = Breadth (number of independent bets per year)
TC = Transfer Coefficient (fraction of the forecast that actually reaches portfolio positions after constraints)

The three terms multiply. Each maps to a different research workstream and a different lever — and in Vietnam, they are not equally improvable:

This map clarifies a common confusion. BR and TC are structural market constraints, not ML problems. They limit every active manager in Vietnam — linear, ML, fundamental, discretionary — to the same ceiling. No model architecture changes them.

So why does ML, specifically, underperform linear models in VN?

Not because of breadth. If breadth were the bottleneck, adding features would not fix overfitting — and yet overfitting is exactly the failure mode we observe.

The real reason is narrower and sharper: ML's only contribution can be to IC. And IC is improved primarily by giving the model better information per observation. ML methods (gradient boosting, deep nets) need many observations relative to their effective degrees of freedom to estimate that mapping without overfitting. In Vietnam — small cross-section, short usable history, regime instability — the data simply does not support the parameter count those models want.

That makes ML's effective contribution path narrow:

  • ML cannot move BR (market structure).
  • ML cannot move TC (mandate / cost structure).
  • ML can only move IC, but IC improvement requires either better inputs or more data — and we are data-constrained at exactly the term ML is supposed to help with.
Implication

The diagnosis "ML doesn't work in VN because the market is small" is too coarse. The accurate version: ML is a tool for the IC term, and the IC term in VN is data-hostile to high-capacity estimators. The correct response is not to swap one model architecture for another — it is to attack the inputs (features) and constrain the estimator (simplicity, regularisation, strong cross-validation).

§2The hypothesis

Given the term map above, the leverage point is unambiguous: improve IC. But there is a second-order point that is easy to get wrong.

Combined IC ≈ ρ · √N
where ρ = average IC of an individual signal, N = number of independent signals combined

Most of the gain in combined IC comes from increasing N (independent signals), not from making any single signal extraordinarily strong. A few very strong features are rare and tend to be correlated — they are often re-labellings of the same underlying mechanism (e.g. multiple "momentum" features that all load on the same factor). Many moderate-strength but mechanism-orthogonal features compound far more reliably.

There is a second benefit: each genuinely independent signal manufactures a fresh independent bet, which raises effective BR. So the same act — adding orthogonal signals — pushes both terms upward simultaneously. This is the only realistic route to escape the structural breadth ceiling of a narrow market.

Hypothesis

If we can assemble a small library of features driven by mechanically independent sources (microstructure flow, foreign positioning, liquidity, dispersion, fundamentals, sentiment, etc.) — each with modest standalone IC but low correlation to the rest — then a simple combiner is enough to lift combined IC above the friction floor. Both IC and effective √BR rise together.

The right question to ask of every candidate is not "is this feature strong?" but "is this feature independent of what we already have?"

Which combiner — and a caveat against defaulting to GBM

"Good features + simple model beats weak features + complex model" is correct ML-in-finance wisdom. But "simple model" in a VN-scale dataset should default to linear (elastic-net / ridge), not gradient boosting:

  • Linear combiners have minimal degrees of freedom; with good features, they extract most of the available IC.
  • They are debuggable: coefficients map directly onto "how much each feature contributes."
  • They sidestep the bias-variance trap that plagues GBM at low sample counts.

GBM is an upgrade to prove, not a default. It must beat elastic-net in purged, embargoed cross-validation, after deflation for the number of model variants tried (Bonferroni or Deflated Sharpe Ratio). Otherwise the apparent gain is the noise of the search.

§3The plan — feature store, starting with microstructure

Strong individual features and (more importantly) mechanism-independent feature mixes require infrastructure: a feature store where each feature is defined once, computed reproducibly, cached, evaluated against a library of existing features, and combined in a versioned pipeline. This is structurally different from one-off notebooks that compute features ad-hoc for a single hypothesis.

Requirements for the feature store

RequirementWhy
Point-in-time correctnessFeature value at date T uses only data observable at T. No future leakage.
ReproducibilitySame raw data → same feature output. Versioned definitions.
CacheableExpensive features (microstructure aggregations from tick data) get computed once, reused often.
ComposabilityFeature A + Feature B → Feature C without rewriting pipelines. Stack survivors freely.
Library-aware evaluationNew features evaluated conditional on the existing library, not in isolation. See §4.

Why start with microstructure

Two reasons. First, price-based features (returns, momentum, MAs, RSI) and fundamentals (PE, PB, ROE) are the most-explored layer of the feature space in VN — any IC they carry is the residual after a crowded set of participants has already extracted what they can. Second, microstructure features are underexplored precisely because tick / orderbook data is expensive to source and process. Less crowding = more residual IC available.

Starting point is a single feature: BUSD processed — the buy-side vs sell-side matched-value imbalance computed from cleaned tick data, with put-through deals excluded. Importantly, BUSD is feature #1 in a library that we then extend with mechanically independent additions, not with twelve BUSD variants:

  • BUSD processed — aggressor-side imbalance from matched ticks. (Feature 1.)
  • Foreign matched flow — different participant class, different decision process. Plausibly orthogonal to BUSD.
  • Liquidity / illiquidity — Amihud-style or depth-driven; price-impact mechanics, not flow direction.
  • Cross-sectional dispersion — regime indicator, not stock-level signal; affects how signals combine.
  • Realised volatility / jumps — second-moment information, orthogonal to mean direction.
  • VWAP deviation — intraday reversion mechanic.

Each addition is justified by a different underlying mechanism. The discipline: don't add another variant of what you already have until you've added something with a different generating process.

Pipeline — feature #1 (BUSD processed)

STEP 01
Define BUSD precisely
BUSDt = Σ(buy-side matched value) − Σ(sell-side matched value) on day t, matched ticks only (put-through deals dropped). Normalise by total matched value on the same day to get a ratio in [−1, +1].
STEP 02
Compute from tick data, cache to parquet
Pull from the orderbook + tick collection, aggregate per (ticker, date), cache PIT-tagged parquet under features/busd/.
STEP 03
Engineer transformations (not duplicates)
Z-score over 20d, persistence (5d sum), shock (today vs 20d mean). These are mathematical transformations of the same signal — treat them as candidate inputs but expect them to be heavily correlated with each other.
STEP 04
Evaluate against the library (initially empty)
Run the §4 IC suite. For the first feature, library is empty so "residual IC" reduces to "raw IC." Record numbers as the starting point.
STEP 05
Stability check
Rolling IC by year, by sector, by regime. A feature survives only if its IC sign and magnitude hold across windows. IC = +0.05 in one regime and −0.03 in another is noise dressed as alpha.
STEP 06
Promote and document
If a variant passes the IC + stability thresholds, store it with metadata: definition, IC statistics, stability profile, correlation against existing library entries. From this point onward, every new candidate is evaluated against this library, not in isolation.

§4Evaluation — a strategy backtest is the wrong tool here

During feature discovery, do not use strategy-level Sharpe as the benchmark. A strategy backtest measures a composite:

Strategy Sharpe = f(signal · construction · sizing · execution)

When a strategy backtest returns negative Sharpe, you cannot tell whether the feature is weak, the construction is wrong, sizing is mis-specified, or execution assumptions are unrealistic. Worse, you cannot tell whether the feature adds anything beyond what your existing library already has — a candidate that mostly replicates an existing feature can look "profitable standalone" and yet contribute zero to the combined portfolio.

✗ STRATEGY-LEVEL BENCHMARK

Sharpe, MaxDD, AnnRet, turnover. Appropriate once a strong combined signal exists and the question is how to harvest it. Wrong during feature discovery — confounds feature quality with construction, and ignores whether the feature is genuinely additive.

✓ INFORMATION-LEVEL, LIBRARY-CONDITIONAL

Residual IC after orthogonalising the candidate against the existing library, measured panel-wide (stock × day), under purged + embargoed cross-validation, with a deflated significance threshold for the number of candidates tried. The benchmark to beat is "library without this feature."

What "library-conditional residual IC" actually means

  1. Orthogonalise. Regress the candidate feature on the existing library, cross-sectionally and on a rolling basis. The residual is the part of the candidate that isn't already captured.
  2. IC on the residual. Compute rank-IC of the residual against forward returns. This is the candidate's marginal contribution.
  3. Purged + embargoed CV. Train on one window, evaluate IC on a non-overlapping later window with a purge buffer between them. Repeat. Reports must reflect out-of-sample IC, not in-sample.
  4. Deflate the hurdle. If you've tried K candidates, the significance threshold for "real" alpha is not 5% — it's roughly 5%/K (Bonferroni), or use the Deflated Sharpe Ratio (Bailey & Lopez de Prado 2014). A candidate that "barely passes" raw t-stat 2 after 50 tries hasn't passed anything.
  5. Library improvement test. Train the combiner with and without the candidate. Compare combined OOS IC and combined OOS IR. The candidate earns a slot only if it improves the library, not just itself.

Pass thresholds for the IC suite

MetricDefinitionThreshold
Residual rank-IC Rank correlation between (candidate orthogonalised against library) and forward return, panel-wise ≥ 0.02
IC t-stat (deflated) t-statistic of the IC time series, with hurdle adjusted for number of candidates tried passes deflated test
IC stability % of rolling windows with IC of the same sign as the full-sample IC ≥ 70%
IC decay half-life Forecast horizon at which IC drops to 50% of its 1-day value ≥ 5 days (preferred)
Library-conditional gain Combined OOS IR with candidate vs without strictly positive after CV noise
Why these and not "individual feature IC ≥ 0.03"

A candidate with raw IC = 0.04 but ρ = 0.95 to an existing library feature has residual IC near zero — it adds nothing. A candidate with raw IC = 0.025 but mechanism-orthogonal to the library can lift combined IC noticeably. The right gate is residual, not raw.

Order of operations

  1. Discover — compute a candidate, run the library-conditional IC suite. Drop immediately on failure.
  2. Validate — re-test on an unseen holdout. Confirm stability across windows.
  3. Promote — add to the library. From now on, future candidates are evaluated against this larger library (the bar gets harder over time — which is correct).
  4. Combine — train an elastic-net combiner on the library. Promote to GBM only if it clears the deflated-CV bar.
  5. Construct — wrap the combined signal in a portfolio process (sizing, weight caps, T+1 lag, sector caps). Only here does the Transfer Coefficient enter.
  6. Backtest — strategy-level Sharpe + bootstrap CI on the full pipeline. This is the last step, not the first, and it evaluates the construction + signal jointly.
  7. Deploy — paper-trade before live.

Steps 1–4 are information-level work: they ask "is the signal real and additive?" Steps 5–7 are harvesting-level work: they ask "given the signal, how much of it can we keep after constraints?" Confusing the two is what makes most quant research in this space frustrating — a perfectly fine feature gets killed by a bad construction at step 1, or a useless feature gets celebrated because the construction happened to mask its weakness.

§5Closing — what this framework commits us to

The three-term decomposition of IR provides a clean accounting of where effort should go:

TermVN statusLeverThis project's commitment
ICImprovableIndependent features, simple combinerBuild feature store; library-conditional evaluation; start with BUSD as feature #1.
√BRStructurally cappedIndependent signals also manufacture effective betsIndirect lift via signal independence.
TCMandate-boundHarvesting design; soft constraintsDeferred to later harvesting layer; not the discovery problem.

ML's role in this framework is modest and well-defined: it is one of several tools for the IC term, used after features are constructed, and constrained by data scarcity at exactly the place it could help most. The honest move is to expect modest ML contribution, to default the combiner to a linear model, and to make any move to non-linear models prove itself under deflated cross-validation.

What this framework commits us to:

  • Stop competing on model architecture. Compete on feature independence.
  • Default to linear combiners. Treat GBM/ML as upgrades that must beat the linear baseline under purged, embargoed, deflated CV.
  • Evaluate features against the library, not in isolation. Residual IC, library-conditional, panel-wide.
  • Reserve strategy backtests for the end. They are construction tests, not feature tests.
  • Add features by mechanism, not by variant. One BUSD, then one foreign flow, then one liquidity — not fifty BUSDs.
